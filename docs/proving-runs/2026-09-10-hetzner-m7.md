# Proving run: M7 metrics, alerting, and alert evidence on a real Hetzner host

| | |
| --- | --- |
| **Date** | 2026-09-10 |
| **Scope** | M7 exit criteria: induced failure raises a declared alert with evidence, audit reports alert-rule compliance |
| **Host** | Hetzner Cloud cx23 (fsn1), stock Debian 13.6 image, deleted after the run |
| **Verdict** | All criteria met; one latency finding found and fixed live |

## Method

A disposable cx23 was created from the stock `debian-13` image with a
throwaway ed25519 key and destroyed at the end of the run. A dedicated state
directory declared the host honestly (ext4 root, no RAID, default-deny
firewall with only SSH) plus the full M7 surface: a PostgreSQL 17 service
with `metrics.enabled`, a single-host `LoggingStack` (Loki 3.7.7, Grafana
13.2.1, Alloy 1.19.2-1) with an `alerting` block — loopback Alertmanager and
one declared webhook receiver — and a `postgresql-down` AlertRule
(`pg_up{service="postgresql-main"} == 0`, `for: 1m`, critical). Scrape
interval 15 s. Throwaway mTLS material and the Grafana password were
pre-provisioned at the documented paths; the gateway name resolved via an
`/etc/hosts` entry on the single host. A local loopback HTTP listener stood
in for the webhook destination so delivery could be proven.

Only public entry points were used: `cloudfall state validate`,
`cloudfall-engine inventory render`, the `baseline.yml`, `services.yml`,
`logging.yml`, and `inspect.yml` playbooks, and `cloudfall audit`.

## Results

- **Deploy**: baseline (40 ok / 0 failed), services (26 ok / 0 failed),
  logging with alerting (79 ok / 0 failed) all converged first try. The
  postgres exporter connected over the local socket as the peer-authenticated
  `alloy` role — no password anywhere — and `pg_up` arrived in the loopback
  Prometheus labeled `service="postgresql-main", server="hz1",
  environment="production"` through the mTLS remote-write gateway. The
  declared rule loaded as `postgresql_down` with `health: ok`; Alertmanager
  answered ready on its declared loopback port with clustering disabled
- **Baseline audit**: 20/20 checks compliant, including the new
  `alerting.rules[postgresql-down]` check backed by the live Prometheus rules
  API captured in the observation
- **Induced failure**: `systemctl stop postgresql@17-main` at T0. The alert
  went **pending at T0+28 s** (within the one-minute exit criterion),
  **firing at T0+86 s** (the declared `for: 1m` dampening plus one
  evaluation boundary), and the declared webhook received the full firing
  payload — alertname, `cloudfall_rule: postgresql-down`, severity, service
  labels, summary — at **T0+115 s** after Alertmanager's 30 s group wait
- **Evidence under failure**: the mid-failure audit reported overall
  **drift** — `services.bind[postgresql-main]` had no listener, which is the
  truth — while `alerting.rules[postgresql-down]` stayed **compliant with
  `state: firing`** in its observed value, and the observation's alert
  evidence carried the firing alert. Firing is status, not drift; a dead
  service is drift. The two signals separated exactly as designed
- **Recovery**: after `systemctl start postgresql@17-main` the alert
  resolved in 27 s and the final audit returned 20/20 compliant

## Findings

1. **Alert evaluation was bounded by Prometheus's 1-minute default.** The
   managed Prometheus config set the scrape interval from the declared
   collection interval but left `evaluation_interval` at the 1 m default, so
   detection latency could not benefit from faster scraping. The template now
   sets `evaluation_interval` from the same declared interval; the fix was
   applied mid-run (redeploy: 3 changes) and the measured 28 s
   pending latency reflects it

## Caveats

- Single-host topology: backend, collector, and the failing service shared
  one machine; multi-host alert flow is unexercised
- The webhook destination was a loopback listener; a real external receiver
  (and the email channel) remain unexercised, though the email config path is
  covered by template tests
- The `for: 1m` dampening means end-to-end notification lands at ~2 minutes;
  that is declared policy, not pipeline latency — a rule with `for: 15s`
  would notify correspondingly faster
