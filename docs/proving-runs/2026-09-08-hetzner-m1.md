# Proving run: M1 baseline and observability on a real Hetzner host

| | |
| --- | --- |
| **Date** | 2026-09-08 |
| **Scope** | M1 exit criteria: idempotent baseline, compliant audit, live host metrics |
| **Host** | Hetzner Cloud cx23 (fsn1), stock Debian 13 image, deleted after the run |
| **Verdict** | All criteria met; two engine/schema bugs found and fixed |

## Method

A disposable cx23 server was created from Hetzner's stock `debian-13` image
with a throwaway ed25519 key and destroyed at the end of the run. A dedicated
state directory declared the host honestly: ext4 root, no software RAID,
firewall allowing only `tcp/22`, the standard package/service/timer
requirements, and a single-host `LoggingStack` (Loki 3.7.7, Grafana 13.2.1,
Alloy 1.19.2-1) in which the same server is backend and collector, with
throwaway mTLS material placed at the documented paths per the logging
service guide.

Only public entry points were used: `cloudfall state validate`,
`cloudfall-engine inventory render`, the `baseline.yml`, `inspect.yml`, and
`logging.yml` playbooks, and `cloudfall audit`.

## Results

- **Baseline**: first run converged with zero failures (the firewall template
  fix from the [container proving
  run](2026-09-08-debian-container-m1.md) held on real hardware); the SSH
  control connection survived the default-deny nftables cutover. Second run
  reported `changed=0` — idempotent
- **Audit**: `cloudfall audit` exited `0` with 18/18 checks compliant after
  finding 1 below was fixed, and again at the end of the run with the full
  logging stack deployed
- **Observability**: Loki, Grafana, Prometheus, Alloy, and the Nginx mTLS
  gateway all active. Journal log streams arrived in Loki through the
  client-certificate gateway, and host metrics from Alloy's embedded unix
  exporter (`node_memory_MemTotal_bytes` reporting the machine's real 4 GB,
  `node_load1`, labeled `job=integrations/unix, server=hz1`) were queryable
  from the loopback Prometheus. The second `logging.yml` run reported one
  residual change (task not captured), the third reported `changed=0`

## Findings

1. **The observation schema rejected real systemd unit names.** The host
   reported `systemd-fsck@dev-disk-by\x2duuid-….service` (systemd escapes
   dashes in device-instance units), which the shared declared-state pattern
   refused, so inspection output failed validation before the audit could
   run. Observed-evidence unit names now have their own pattern accepting
   systemd escapes, while declared state stays strict; a regression test
   covers the escaped form. A container host never surfaces such units, so
   this was only findable on real hardware
2. **First logging deploy on a fresh host always failed.** The logging roles
   add the Grafana APT repository and then install pinned packages with
   `cache_valid_time: 3600`; because the baseline had refreshed the cache
   minutes earlier, the new repository's index was never read and the pin was
   reported unavailable. Both roles now force a cache refresh when the
   repository task reports a change. The fix was proven live by removing the
   repository from the host and re-running the deploy from that state

## Caveats

- A cloud VPS is still not the wedge's bare-metal target: software RAID and
  the storage-provisioning path remain unexercised
- The logging stack ran single-host (backend and collector on one machine);
  a multi-host collector topology remains unexercised
- M2–M5 layers (service catalog, deploy slice, importer, migrate
  orchestrator) were not in scope and remain unproven live

## Cost

One cx23 instance for under two hours: a few euro cents.
