# Proving run: M4 import and M5 agent-driven migration on a real Hetzner host

| | |
| --- | --- |
| **Date** | 2026-09-08 |
| **Scope** | M4 (blueprint import) and M5 (full migration through MCP by an AI agent) |
| **Host** | Hetzner Cloud cx23 (fsn1), stock Debian 13 image, deleted after the run |
| **Verdict** | Both exits met; the migration ran bare-Debian → HTTPS in ~7.5 minutes |

## Method

An AI agent (Claude, driving `cloudfall-mcp` as a stdio MCP client) performed
the migration end to end. Every server-changing action went through the MCP
tool surface with its confirmation handshake; the agent had no shell access
to the server during the migration (SSH was used once before it started, to
wait for the fresh host to boot).

The input was a realistic `render.yaml` blueprint: a Python web service with
`startCommand`, `healthCheckPath`, env vars, and a custom domain, plus a
managed PostgreSQL database with a declared user. The custom domain was an
`sslip.io` name resolving to the host so DNS verification and Let's Encrypt
issuance ran for real.

## Results

- **M4 import** (`import_render` MCP tool): the blueprint became a
  validated config fragment — one application, one component (argv service
  command with `$PORT`, HTTP health check), one loopback PostgreSQL 17
  service with an application-owned database, one TLS-required domain — plus
  an environment file kept outside the config and a seven-item gap report
  whose required actions (uv.lock present, env file review, DNS pointing,
  Render-side data dump) the agent worked through before migrating
- **M5 migration** (`migrate` MCP tool): the preview call returned a ten-step
  plan; the `confirm=true` call executed all ten — baseline, PostgreSQL,
  artifact build, health-gated deploy, HTTP routes, DNS verification against
  the declared proxy, TLS issuance, evidence collection, a compliant 20/20
  audit, and a route-health pass — in roughly 7.5 minutes of wall time
- **Resumability**: a later `migrate confirm=true` call in a fresh MCP
  session read the persisted plan and reported all ten steps completed with
  zero re-runs
- **Independent verification**: `https://app.188.34.153.101.sslip.io/health`
  returned 200 over HTTP/2 with a valid certificate from outside;
  `services_status` reported the route healthy end to end and
  `component_health` returned `healthy: true`
- The systemd `"$PORT"` expansion path works: the imported argv command took
  its port from the generated environment file through `EnvironmentFile`

## Findings

1. **Single-host routes could never pass the final evidence gate** (carried
   over from the M2/M3 run, fixed here): the origin probe timed out against
   the firewall whenever origin and proxy share one host, degrading the
   route to a warning that `verify-routes` treats as failure. Domain
   inspection now records an explicit origin skip ("origin shares the proxy
   host; covered by the public probe") and operations treats it as healthy;
   regression-tested
2. **Imported environment files duplicated `PORT`.** A blueprint that
   declares `PORT` in `envVars` got the line twice (the claimed port is
   prepended). Fixed with a test
3. **The importer assumes environment `production`** and has no flag to
   choose another, so fragments only merge with servers declared in
   `production`; cross-reference validation catches the mismatch loudly.
   Recorded as a DX gap, not fixed

## Caveats

- The source application was a synthetic blueprint and repository, not an
  application actually hosted on Render: the Render API path, a real data
  dump/restore from Render's managed PostgreSQL, and a real DNS TTL cutover
  (sslip.io needs no record change, so `dns-verify` passed without the pause
  a real migration would hit) remain unexercised
- Same cloud-VPS caveats as earlier runs: no software RAID or bare-metal
  storage provisioning
