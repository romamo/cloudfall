# Proving run: M2 service catalog and M3 deploy slice on a real Hetzner host

| | |
| --- | --- |
| **Date** | 2026-09-08 |
| **Scope** | M2 exit (PostgreSQL + Nginx/TLS, audited) and M3 exit (deploy, auto-rollback) |
| **Host** | Hetzner Cloud cx23 (fsn1), stock Debian 13 image, deleted after the run |
| **Verdict** | Both exits met end to end; six engine/CLI bugs found and fixed |

## Method

A disposable cx23 server was created from Hetzner's stock `debian-13` image
and destroyed after the run. The config declared a `demo` application with a
`demo-api` component (a minimal uv-locked ASGI app in a local `file://` git
repository with a healthy `main` branch and a `broken` branch whose `/health`
returns 500), a loopback PostgreSQL 17 service with a project database, and a
TLS-required `Domain` on `app.188.34.153.101.sslip.io` — a name that publicly
resolves to the host, so Let's Encrypt HTTP-01 issuance could be proven
without owning a domain. Only public entry points were used.

## Results

- **Baseline**: converged and idempotent (`changed=0` on the second run)
  with the component and application declared, exercising the bootstrap
  scaffolding (application user, `/srv/apps/demo/api` release directories)
- **M2 PostgreSQL**: deployed and idempotent; bound to `127.0.0.1:5432`
  only (socket evidence in the audit); `sudo -u demo psql -d demo` connects
  via peer authentication with no password
- **M3 deploy slice**, all through `cloudfall` CLI commands with structured
  JSON results:
  - `deploy` of the healthy release: digest-verified transfer, locked
    dependency materialization via pinned uv, systemd unit, health gate,
    symlink switch, release receipt — service active, `/health` 200
  - `deploy` of the broken release: the health gate failed and the engine
    **rolled back automatically** to the previous release; the CLI exited
    `1` with the rollback recorded, and the host stayed healthy on the good
    release throughout
  - `health` and `restart` both returned `healthy: true`
- **M2 Nginx/TLS**: the domain route went live with a real Let's Encrypt
  certificate issued via webroot HTTP-01 —
  `https://app.188.34.153.101.sslip.io/health` returned 200 over HTTP/2
  through the Nginx proxy to the loopback app; certbot renewal timer enabled
- **Evidence**: final audit compliant, 20/20 checks (packages, services,
  timers, firewall with 22/80/443, listening sockets, sshd and vhost
  configuration hashes); `services status` lifecycle reached
  planned/ready/deployed/configured with DNS, TLS, and public checks healthy

## Findings (all fixed in this run)

1. **Bootstrap argument spec rejected rendered components.** The inventory
   renderer emits rich component objects for the deploy layer, but the
   strict `cloudfall_bootstrap` argument spec accepts only its four
   scaffolding fields. Any config with a component failed the baseline. The
   playbooks now project the bootstrap fields at the boundary; the role
   spec stays strict
2. **`include_role`-in-loop variable collision.** Playbooks bound role
   variables to `"{{ item }}"` lazily; roles with inner loops shadowed
   `item`, so the PostgreSQL role saw a database owner string where it
   expected the service object, and the deploy role saw a path. Every
   component/service/domain playbook now uses an explicit `loop_var`
3. **Relative artifact paths broke deploys.** The CLI handed `--artifacts`
   paths to the engine unresolved, so Ansible searched its role directories;
   the documented `task deploy` defaults could never work. Controller-side
   paths are now resolved to absolute at the API boundary
4. **Receipt directories were never created.** Both the deploy and nginx
   roles wrote controller-side receipts into directories they did not
   create, failing after an otherwise successful convergence. Both roles now
   ensure the directory exists
5. **Non-default branches could not be built.** `git checkout --detach
   <branch>` collides with git's remote-branch DWIM on a fresh clone. The
   builder now resolves the ref (branch, tag, or commit; local then
   `origin/`) to a commit first; a regression test builds a feature branch
6. **`ISSUE_CERTIFICATES=true` could never issue.** Extra-vars arrive as
   strings and ansible-core 2.19 rejects non-boolean conditionals, and
   certificate issuance ran before any vhost served the ACME webroot, so
   the challenge always 404ed. The flag is now coerced with `| bool`, and
   the role brings the HTTP-only vhost live first, issues the certificate,
   then re-renders with TLS

## Open finding (not fixed)

The `services status` origin check probes the origin port from outside; on a
single-host topology the default-deny firewall rightly blocks it, so the
wedge's one-host story always reports a false origin warning. The origin
check needs a single-host mode; tracked for the M4 cutover work.

## Caveats

- Controller-side receipts rewrite on every run (fresh timestamp), so a
  re-run reports one controller change; host-side convergence is `changed=0`
- The app was a synthetic minimal ASGI service, not a real Render workload;
  M4's importer path (render.yaml → config → migrate) remains unproven live
- Same cloud-VPS caveats as the M1 run: no software RAID or bare-metal
  storage provisioning
