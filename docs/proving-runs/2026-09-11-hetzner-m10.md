# Proving run: M10 restore drill and external alert delivery

| | |
| --- | --- |
| **Date** | 2026-09-11 |
| **Scope** | M10 exit criteria: a scheduled backup is restore-verified by the timer-driven drill with a schema-valid `BackupReceipt`, and an induced failure delivers an alert to a real external destination |
| **Hosts** | Two Hetzner Cloud cx23 (fsn1), stock Debian 13.6 images, deleted after the run |
| **Verdict** | All criteria met; one inventory-rendering bug found and fixed live |

## Method

Two disposable cx23 hosts were created from the stock `debian-13` image with
a throwaway ed25519 key and destroyed at the end of the run: a proving host
carrying the full stack, and a separate **alert-sink host** running only a
15-line Python HTTP listener appending every request body to a log — the
"real external destination" that a loopback listener cannot stand in for.

A dedicated config directory declared the proving host honestly (ext4 root,
no RAID, default-deny firewall with only SSH) plus the M10 surface: a
PostgreSQL 17 service with `metrics.enabled`, scheduled backups, and the new
`backup.restoreCheckOnCalendar` drill schedule; both
`cloudfall-postgresql-backup.timer` and
`cloudfall-postgresql-restore-check.timer` declared as required units; a
single-host `LoggingStack` (Loki 3.7.7, Grafana 13.2.1, Alloy 1.19.2-1) with
an `alerting` block whose one receiver was a webhook pointing at the sink
host's public address; and the `postgresql-down` AlertRule
(`pg_up{service="postgresql-main"} == 0`, `for: 1m`, critical). The `crm`
database was seeded with 1,000 rows before any backup ran.

Only public entry points were used: `cloudfall config validate`,
`cloudfall-engine inventory render`, the `baseline.yml`, `services.yml`,
`logging.yml`, and `inspect.yml` playbooks, `cloudfall backup verify`, and
`cloudfall audit`.

## Results

- **Deploy**: baseline (40 ok / 0 failed), services (0 failed, installing
  both the backup timer and the new restore-drill timer), logging with
  alerting (75 ok / 0 failed). `systemctl list-timers` showed the backup
  scheduled at 02:00 UTC and the restore drill at 05:00 UTC
- **Timer-driven restore drill**: after a real dump of the seeded database,
  starting the timer's own service unit
  (`cloudfall-postgresql-restore-check.service`) restored the newest dump
  into a scratch database, counted 420 catalog relations, dropped the
  scratch, and logged `restore check passed` — the exact path the 05:00
  timer fires continuously from now on
- **Schema-valid receipt**: `cloudfall backup verify` executed the same
  drill through the engine's backup contract and wrote a validated
  `BackupReceipt` (`action: restore-check`, the dump path and relation count
  in its summary)
- **Baseline audit**: 21/21 checks compliant, including
  `services.required[cloudfall-postgresql-backup.timer]` and
  `services.required[cloudfall-postgresql-restore-check.timer]` — the drill
  is audited like any other unit, meeting the "scheduled drill" bullet
- **Induced failure**: `systemctl stop postgresql@17-main` at T0 17:19:07
  UTC. The mid-failure audit separated the signals exactly as designed:
  `services.bind[postgresql-main]` reported **drift** (no listener — the
  truth) while `alerting.rules[postgresql-down]` stayed **compliant** with
  observed `state: pending`
- **External delivery**: the alert fired at T0+83 s and the sink host —
  a different machine across the public network — logged the full firing
  payload at **T0+113 s**: alertname, `cloudfall_rule: postgresql-down`,
  severity, service and server labels, and the summary, arriving from the
  proving host's address. The resolved notification followed after recovery
- **Recovery**: after `systemctl start postgresql@17-main`, the final audit
  returned 21/21 compliant

## Findings

1. **The typed inventory silently dropped the new backup field.** The schema
   accepted `restoreCheckOnCalendar` and the role guarded on it, but
   `ServiceBackup` in the SDK did not model the field, so the rendered
   inventory omitted it and the first services run installed no drill timer
   — no error anywhere, just a missing unit. The audit's required-timer
   check caught it. `ServiceBackup` now carries the optional field
   end-to-end, with the inventory tests updated to prove it

## Caveats

- The drill and the delivery were exercised by starting the timers' service
  units directly rather than waiting for the 05:00 wall-clock firing; the
  timers themselves are audited as enabled and scheduled
- The webhook receiver delivered over plain HTTP to a throwaway sink; the
  email channel remains unexercised end to end (its config path is covered
  by template tests)
- The sink accepted from any source; a production receiver should
  authenticate the sender
